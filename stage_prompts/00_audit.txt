## Objective
Read the entire web project source — every line of every frontend and backend file —
and produce FEATURE_PARITY_REGISTRY.md: a complete atomic feature checklist that the
macOS build agent MUST check off before marking any screen as done.
Every missed feature becomes a missing screen. Read exhaustively.

- Backend lives under `server/` (this project does NOT use `src/backend/`).
  Discover all Flask/FastAPI/Express blueprints/routers under `server/`.

Wherever the audit-prompt boilerplate below says `src/frontend/index.html`, read

## Target State
A single file FEATURE_PARITY_REGISTRY.md exists in the project root containing:
- Every atomic feature, tab, toggle, modal, form, table, chart, and action
  found in the web app — with zero omissions
- Each item has a unique ID (F-001, F-002...) and a macOS status column (default: ❌)
- The registry is machine-readable by the build agent as a checklist
- Every API endpoint called from the frontend is mapped to a registry item
- Every business rule triggered by a UI action is mapped to a registry item

## Reading Strategy — MANDATORY, follow exactly

### Step 1 — Map the file before reading it
Do NOT attempt to read web/index.html in one pass.

```bash
# Line count
wc -l web/index.html

# Navigation section boundaries
grep -nE "nav|section|data-page|data-tab|data-view|id=\"page-|id=\"tab-|id=\"section-|class=\"page|class=\"tab-content|class=\"view" web/index.html | head -200

# Function definitions (user actions)
grep -nE "^function |^  function |^    function |^const.*= function|^const.*=.*=>" web/index.html | head -300

# fetch calls (API integrations)
grep -nE "fetch\(|\.then\(|async function|await fetch" web/index.html | head -300

# Event listeners (interactive elements)
grep -nE "addEventListener|onclick|onchange|onsubmit|onkeyup|onkeydown" web/index.html | head -300

# Modals / dialogs / panels
grep -nE "modal|dialog|panel|drawer|popover|overlay|sheet" web/index.html | head -200

# Charts / visualizations
grep -nE "chart|Chart|canvas|svg|graph|viz|sankey|sparkline|ring|donut|bar|pie" web/index.html | head -100
```

Record the line number ranges for each logical section before reading any section.

### Step 2 — Read every supporting frontend file
```bash
ls web/
# Read every .js / .css / .html under web/ — every line
```

### Step 3 — Read web/index.html in chunks of 2,000 lines
Use Read with explicit line ranges. Never skip a range.
For each chunk: extract every UI element, action, state, and API call found.
Add each to the registry immediately — do not batch at the end.

### Step 4 — Read all backend files under server/
```bash
ls server/
find server -name "*.py" -o -name "*.js" -o -name "*.ts" | head -50
```
For each route file:
- Read the file completely
- Extract every route: method, path, auth requirement, request shape, response shape
- Map it to the frontend fetch() calls found in Step 1
- Flag any frontend fetch with no backend route as [UNCOVERED-API]

### Step 5 — Read the backend schema completely
Find any `schema.py`, `models.py`, `migrations/`, or DB-init file.
For each model: confirm every field is represented in at least one registry item.
A field with no UI representation is [BACKEND-ONLY] or [MISSING-FROM-UI].

## Registry Format — MANDATORY structure

```markdown
# Feature Parity Registry
# Generated by Deep Audit — <date>
# Total items: <N>
# Source: web/index.html <line count> lines + <N> backend route files

## HOW TO USE
The macOS build agent MUST:
1. Before implementing any screen: search this file for all items where Screen = that screen
2. Implement every item for that screen — no exceptions
3. Change status from ❌ to ✅ when implemented, 🔄 if adapted for desktop
4. Do NOT mark a screen complete until every item for it is ✅ or 🔄

## REGISTRY

### GROUP: <Feature Group Name>
#### Screen: <Screen Name>

| ID | Feature | UI Element | Sub-tab / Modal | API Call | Business Rule | macOS Impl | Status |
|----|---------|-----------|-----------------|----------|---------------|------------|--------|
| F-001 | <atomic feature> | <button/table/form/chart/badge/etc> | <parent tab or modal name, or —> | <GET/POST /endpoint or —> | <rule enforced or —> | <SwiftUI component or TBD> | ❌ |
```

Rules for registry entries:
- ONE row per atomic feature — not one row per screen
- "Atomic" means: one user action, one display element, one state, or one business rule
- Modals are separate rows from the screen that opens them
- Each tab within a tabbed view is a separate group of rows
- A table with N columns is N rows
- A form with N fields is N+ rows (fields + submit + validation)
- Loading state, empty state, error state are separate rows from happy path
- Inline edit is a separate row from the read-only display
- Every chart, every badge, every status indicator is its own row

Forbidden shortcuts:
- NEVER "all fields" — list each field individually
- NEVER "standard CRUD" — list each operation
- NEVER omit because "seems minor"
- NEVER skip a modal
